# 23 — Internationalization (i18n)

Even if multiple languages aren't launched immediately, the architecture must support i18n from the start. Adding i18n retroactively means restructuring every route in the app. The URL structure decision is the critical one — it must be made before the app scales.

---

## URL Structure Decision (Make This First)

Two approaches, and they are mutually exclusive route-structure choices:

- **Locale in URL path:** `/en/products`, `/fr/products`, `/hi/products` — clean, cacheable, indexable by search engines. Requires restructuring all routes to `app/[locale]/...`. This is the approach Next.js i18n officially supports in App Router.
- **Middleware-based (subdomain or cookie):** `en.shop.com`, `fr.shop.com` — no URL change but requires DNS config. Or cookie-based — bad for SEO (same URL serves different languages, crawlers can't index them separately).

**Recommendation: locale in URL path.** Restructure `app/` to `app/[locale]/` when i18n is implemented.

---

## Items to Implement

### Architecture

- [x] **Restructure to `app/[locale]/`** — move all current routes under a `[locale]` dynamic segment:
  ```
  app/
    [locale]/
      layout.tsx         ← locale-aware root layout
      page.tsx           ← homepage
      products/
        page.tsx
        [slug]/
          page.tsx
      cart/page.tsx
      ...
  ```
  `middleware.ts` detects the user's preferred locale (from `Accept-Language` header, cookie, or URL) and redirects to the appropriate locale prefix.
  - Complexity: Complex (restructures all routes)

- [x] **Translation library** — use `next-intl` (best Next.js App Router support) or `i18next` + `react-i18next`:
  - Store translations in `/locales/en/common.json`, `/locales/fr/common.json`, etc.
  - Access via `useTranslations('products')` hook
  - Complexity: Medium (once route structure is in place)

- [x] **`hreflang` links for SEO** — tell Google which URL is the language equivalent of each page. Add to `generateMetadata` for all pages:
  ```ts
  alternates: {
    languages: {
      'en': 'https://shop.com/en/products',
      'fr': 'https://shop.com/fr/products',
    }
  }
  ```
  - Complexity: Easy (once locale routing works)

- [x] **`<html lang={locale}>` in root layout** — the root layout already has `lang="en"`. Make it dynamic: `<html lang={locale}>`. Screen readers and search engines use this attribute.
  - Complexity: Easy

### Formatting

- [x] **Currency formatting** — never hardcode `$`. Use `Intl.NumberFormat` with the locale:
  ```ts
  new Intl.NumberFormat(locale, { style: 'currency', currency: currencyCode }).format(price)
  ```
  Create a `formatCurrency(amount, locale, currency)` utility in `src/shared/`.
  - Complexity: Easy
  - File: `src/shared/formatters.ts`

- [x] **Date formatting** — order dates, delivery estimates — use `Intl.DateTimeFormat`:
  ```ts
  new Intl.DateTimeFormat(locale, { dateStyle: 'medium' }).format(date)
  ```
  - Complexity: Easy
  - File: `src/shared/formatters.ts`

- [x] **Pluralization** — "1 item" vs "2 items" vs "5 items" varies by language. Use `Intl.PluralRules` or the translation library's built-in plural handling. Avoid string concatenation like `${count} item${count !== 1 ? 's' : ''}`.
  - Complexity: Easy

### RTL Support

- [x] **CSS logical properties** — for RTL languages (Arabic, Hebrew, Urdu), `margin-left` becomes `margin-right`. Use CSS logical properties from the start:
  - `margin-inline-start` instead of `margin-left`
  - `padding-inline-end` instead of `padding-right`
  - `border-inline-start` instead of `border-left`
  - Already partially done: `globals.scss` uses `margin-inline: auto` for `.container`. Audit the rest.
  - Complexity: Medium (audit + replace)

- [x] **`dir="rtl"` on `<html>`** — when locale is RTL, add `dir="rtl"` to the html element. CSS logical properties then mirror the layout automatically.
  - Complexity: Easy (once locale routing works)
